## #57605 (lookahead dropped in align allocation): DOES NOT affect us
- (a) The bug is in the scheduler/KV manager: MambaManager align branch. Our code is byte-identical to the PR's removed lines: `num_tokens = num_tokens_main_model` at STKM:1754 (get_num_blocks_to_allocate) and STKM:1826 (allocate_new_blocks). The #57050 `physical_block_cap` clamp is at STKM:1791. `num_tokens_main_model = computed + new`, which already includes the scheduled drafts; only the drafter's `num_lookahead_tokens` (= K = 5 for MTP) is dropped (v1/core/kv_cache_manager.py:533-535, config/vllm.py:652-657).
- The missing next page (mechanism 1) only hurts if a Mamba-state writer touches column `cdiv(main_end,B)` in that step. We have none:
  - The MTP drafter is full attention with PLE forced off (models/qwen4_exp/nvidia/mtp.py:7, :269). Its KV goes through the normal attention managers, which do honour lookahead.
  - The target's writes all stay at or below `(main_end-1)//B`:
    - verify source column `(seq_len-1)//B` (v1/attention/backends/utils.py:1161; gdn_recoverssm.py:146 keeps column 0 only);
    - commit plan `final_state_col=(nc+commit_len-1)//B` and `boundary col=next_boundary/B-1` with `next_boundary<=nc+commit_len` (model_executor/layers/mamba/ops/recoverssm.py:84-102);
    - postprocess `(nc+num_sampled-1)//B` (v1/worker/gpu/model_states/recoverssm.py:96-102).
  - Under async scheduling the real `main_end` is at most the optimistic one, so the allocator can only over-allocate.
- Mechanism 2 (displaced running-state column) does not exist at base. Null padding comes from `num_tokens_main_model` (STKM:1826, 1860-1869). MaCoredroid's review says the same: "a hazard introduced by lookahead inflation". The PR's `_align_num_skipped_blocks` hunk fixes its own inflation.
- (b) RecoverSSM plays no part: `num_speculative_blocks=0` comes from `use_recoverssm` (model_executor/layers/mamba/abstract.py:77-83). That is exactly the configuration in which MaCoredroid found base and head differ in allocation, but a difference without a writer is harmless.
- (c) Do NOT cherry-pick it. The head regresses 29-30 CPU tests at the rewritten assert (the `+1` hunk at PR STKM:1926-1945 drops `checkpoint_block` from the bound). Admission also estimates 1 block where allocation takes 2, which raises ValueError.

## #57908 (full aligned hit shares the terminal block while writing it): DOES NOT affect us
- (a) The bug is in the KV manager too (PR adds `_aligned_state_cow_reqs`, `add_local_computed_blocks`, and a `cache_blocks` hook). Its premise, that align kernels write in place into the hit block, is false for the V2 path we run. Trace for B after a full hit at C=kB:
  1. The hit block is placed at column k-1 (STKM:1532-1534). Its ref_cnt is above 1 while A holds it, and it is shared via its hash either way. The hit is capped at `num_tokens-1` (kv_cache_manager.py:295), so the remaining query q is at least 1.
  2. `add_request` seeds `state_idx=(C-1)//B=k-1` (MH:121-123).
  3. The fused preprocess sets `src_col=k-1` and `dst=cdiv(C+q,B)-1>=k` (MU:521-543). The precopy reads k-1 and writes a fresh block at column k or later (MU:607).
  4. B's first step is a prefill (non-spec, state column `(seq_len-1)//B>=k`). Every later RecoverSSM step has nc>kB, so `final_state_idx`, `boundary_state_idx` and the replay slot (`replay_ptr+src*rbs`, model_executor/layers/mamba/gdn/recoverssm_gdn.py:380) all land in columns k or higher, which are private.
  5. So the first commit goes into a fresh block. Column k-1 is only ever a copy source.
- Producer A: A writes column k-1 only in steps with `nc<kB`. The last such step is the one that publishes the hash (the cache cap at `request.num_tokens`, kv_cache_manager.py:602-606; for a=1 the commit writes final and boundary into k-1 with the state after exactly kB tokens). Same-step consumers are deferred (`cached_blocks_this_step`, STKM:1723-1731), and later consumers come after it in stream order.
  - Once nc=kB, the running column is k-1 (after today's off-by-one fix), but the next step's precopy moves it to column k before the forward. Column k-1 is never rewritten.
- (b) The in-place hazard the PR describes exists only for partial tails, meaning hash units of 64 inside a block, and there the existing CoW already handles both sides: the producer by `move_block_hashes` (STKM:1893-1921) and the consumer by `_apply_cow` (STKM:451-471, :1926). The PR leaves that path unchanged.
- (c) If it merges upstream, the effect on us is cost, not correctness: one extra block and one extra state copy per full aligned hit or boundary publish. It also breaks 7 existing tests, including `test_dcp_partial_hit_resumes_on_replicated_mamba_snapshot`.
