A pointer, not a diagnosis — from a different model on the same box class. We spent today on a Qwen3.8-Flash-Next corruption in vLLM (vllm-project/vllm#55357 → #55375) and this one is *not* that: ours needs speculative decoding configured and two prompts prefilled in the same scheduler step, and it garbles a request from its second token on. Your `max-num-seqs 1`, spec-independent, one-token-in-750 pattern rules both out.

What your fingerprint does match is a different class: isolated wrong tokens, not reproducible at a fixed position, with a *small recurring top-5 across unrelated prompts*, is what the sparse attention path produces when it attends to KV rows it was never given — an uninitialised or stale index. vLLM fixed exactly that today for DeepSeek-V4 on the prefill side: vllm-project/vllm#55299 (merged 2026-09-05 10:31 UTC) — the caller-supplied sparse-index workspace was not seeded with the `-1` sentinel that `topk_length` pairs with, so padding columns reached `flash_mla_sparse_fwd` as KV indices (their instrumentation saw `idx_max=2113501039` against `kv_rows=2`). Your symptom is in decode and on a stack whose sparse-MLA decode kernels come from SparkInfer on a vLLM fork rooted at a July commit (`30038602`, long before #55299), so the decode-side analogue there — how the top-k index padding is initialised on the caller-supplied-workspace path, and whether it is re-seeded when the workspace rotates — is where I would look first. It would explain every invariance in your ladder (graphs, sampler, prefix cache, spec on/off), since none of them touch index padding.

A cheap discriminator: at an affected step, dump the selected KV indices for that position and check for values outside the sequence's row count. If any are out of range, it is this class.
